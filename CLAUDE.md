# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Phoenix Park Deer Tracker — a crowdsourced web app for pinning and browsing deer sightings in Phoenix Park, Dublin. Users add sightings by clicking the map or tapping "Found a deer here!" (geolocation), and sightings can also be bulk-imported from Garmin GPX exports.

**Direct Garmin Connect API sync was tried and abandoned** — the unofficial `garmin-connect` npm package only supports Garmin's classic username/password login, not SSO/federated login (Google/Apple/etc.), which is what this project's Garmin account uses. Confirmed by an actual failed login attempt, not just reading docs. Don't re-attempt this without a different underlying library or the official Garmin Developer API (which requires applying for access and a public HTTPS webhook endpoint this local-only app doesn't have).

The actual application lives entirely under `phoenix-deer/`. The repo root's `package.json` is a vestigial leftover (a handful of stray deps, no scripts) — ignore it; it is not the app manifest.

## Commands

Run backend and frontend in separate terminals; there is no single combined dev script.

```bash
# Backend (Express API), from phoenix-deer/
npm run dev          # nodemon server.js, auto-restart
npm start             # node server.js
npm run build          # builds client/ and copies the output into public/ (see Deployment below)

# Frontend (Vite + React), from phoenix-deer/client/
npm run dev           # Vite dev server on :5173
npm run build         # tsc -b && vite build
npm run lint          # eslint .
npm run preview
```

There are no automated tests in this project (backend or frontend).

Backend needs `phoenix-deer/.env` (see `phoenix-deer/.env.example`): `PORT`, `MONGODB_URI` (Mongo must be reachable; db name is hardcoded to `phoenix_deer` in `server.js` via `mongoose.connect(..., { dbName: 'phoenix_deer' })`, independent of whatever db name is in the URI), `SESSION_SECRET` (random signing key), and `ADMIN_PASSWORD_HASH` (bcrypt hash for the `/admin` login — generate with `node scripts/hash-password.js`, run from `phoenix-deer/`; without it set, admin login always fails with a clear "not configured" error rather than silently accepting anything). **`.env` is gitignored — never commit it** (it was accidentally tracked and pushed early in this repo's history; that leak has since been rotated and scrubbed from git history, but don't repeat it).

Open the app at `http://localhost:5173`.

## Architecture

**Backend — single-file Express app (`phoenix-deer/server.js`)**. Everything lives in this one file: middleware setup, the Mongoose `Sighting` schema/model, GPX parsing, all routes. There's no router/controller/model split to navigate — read this file directly rather than searching for a structure that doesn't exist.

- `Sighting` schema: `{ lat, lng, description, location, createdAt, updatedAt }`. `location` is a GeoJSON `Point` (`[lng, lat]`) with a `2dsphere` index, used for proximity-based dedup via `$near` — not just lat/lng scalars filtered in application code. A startup migration backfills `location` on any doc saved before this index existed.
- Routes: `GET/POST /api/sightings` (fully public — anyone can mark a sighting, by design), `POST /api/import-gpx` (multer file upload), `POST /api/import-garmin` (reads all `.gpx` from a local `Garmin/GPX/` folder one level above `phoenix-deer/`), `GET /api/import-stats` — the latter three are **admin-only**, gated by `requireAdmin` (see below).
- `saveSightingsFromFile()` is the shared import path used by every GPX-based route. Dedup is two-layered: within a single import batch (in-memory Haversine check against sightings already queued from the same file, so two near-duplicate waypoints in one GPX don't both insert), then against the DB via an indexed `$near` query (`DEDUP_RADIUS_METERS = 15`) plus exact `createdAt` match. `POST /api/sightings` (manual map-click/geolocation submissions) has its own dedup since it has no caller-set timestamp to match exactly: a `$near` query within a short rolling window (`MANUAL_DUPLICATE_WINDOW_MS = 10s`) catches accidental double-submits and returns the existing doc instead of creating a new one.
- `parseGPXFile()` looks for `<wpt>` entries first, then falls back to track points, then route points. It flags entries as deer sightings by matching the word "deer" (and translations) in the waypoint name/description, replacing the description with a 🦌 emoji string when matched.
- Static frontend build is served from `phoenix-deer/public/` by the same Express app in production. `npm run build` (from `phoenix-deer/`) builds `client/` and copies its output into `public/` — `public/` itself is gitignored (fully regenerated by that script, never commit it). A catch-all `app.get(/^(?!\/api).*/, ...)` route (after `express.static` and all `/api/*` routes) serves `public/index.html` for any other path, so a direct browser navigation/refresh on `/admin` doesn't 404; it 404s with an explanatory message if `public/` hasn't been built yet. No-op in dev (Vite's own dev server handles `/admin` directly).
- `helmet()`'s default CSP only allows `img-src 'self' data:`, which silently breaks the map (OSM tiles, the deer marker icon, the Leaflet marker-shadow image are all external) the moment the app is served by this Express server instead of Vite's dev server — Vite dev isn't behind helmet at all, so this never showed up until the build wiring above actually existed and got tested. Fixed by extending (not replacing) helmet's default `img-src` directive with the three external hosts `App.tsx` actually uses. If a new external image source gets added to the frontend, it needs to be added here too or it'll silently fail the same way (blank/broken image, no visible error unless you check the CSP header or console).
- **Admin auth** (`phoenix-deer/auth.js`) — same "satellite module, not another 500 lines in `server.js`" precedent as the removed `garminClient.js`. Session-cookie based, backed by `connect-mongo` (sessions persist in the `sessions` collection in the same DB — a plain in-memory store would lose every session on each `nodemon` restart). `requireAdmin` middleware 401s unless `req.session.isAdmin`. Login (`POST /api/admin/login`, its own stricter rate limit) compares against `ADMIN_PASSWORD_HASH` via `bcryptjs`; `POST /api/admin/logout` destroys the session; `GET /api/admin/me` reports current state. There's no user table — single hardcoded admin, one password, set via `node scripts/hash-password.js` (masks input, prints the hash to paste into `.env`; never pass a real password to an AI session to generate this).

**Frontend — two pages, no router library** (`phoenix-deer/client/src/main.tsx` does a plain `window.location.pathname === '/admin'` check — adding `react-router` for one extra page was judged not worth it):
- `App.tsx` — the public map. Nearly all state and logic lives in this one component: fetching sightings, the "add marker on click" map handler, geolocation "found a deer here" button, date filtering (Today/This Month/This Year/All), proximity-based marker clustering (custom Haversine-distance grouping within 100m — separate from and not the same as `leaflet.markercluster`, which is a dependency but not wired into `App.tsx`), and an `isAdmin` check (`GET /api/admin/me` on mount) that gates whether the "Import Garmin" button renders at all — logged-out visitors don't see it, not just get a 401 if they somehow clicked it.
- `AdminLogin.tsx` — the entire admin login/logout UI. Not linked from anywhere in the public UI; reached only by knowing to navigate to `/admin` directly. Logging in redirects to `/`.
- All fetches use relative `/api/...` paths, routed through the Vite dev proxy (`vite.config.ts`, proxying `/api` → `http://localhost:5050`) in dev, and same-origin when served from `public/` in production — this also means the session cookie round-trips correctly without any CORS/credentials config, since everything looks same-origin to the browser either way.
- Marker grouping/clustering (`groupSightings`) runs on every render over the currently filtered sightings — fine at current data volumes (~tens of records) but worth knowing if this becomes a perf question later.

**Adjacent untracked directories** — `Garmin/` (raw GPX exports consumed by `/api/import-garmin`) and `solid-data-wallet/` (an unrelated Expo/React Native project) sit in the repo working tree but aren't part of DeerFinder's git history. Don't treat code in `solid-data-wallet/` as part of this app.

## Deployment

**Render** (Node web service, deploys from this GitHub repo) + **MongoDB Atlas** (free M0 cluster). Render service settings: Root Directory `phoenix-deer`, Build Command `npm run build`, Start Command `npm start`, Health Check Path `/api/health`. Required Render environment variables (set in Render's dashboard — never committed anywhere): `MONGODB_URI` (the Atlas connection string), `SESSION_SECRET` (a fresh random value — same one-liner as local setup, `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`, but generate a separate one for prod), `ADMIN_PASSWORD_HASH` (via `node scripts/hash-password.js`, same as local), `NODE_ENV=production` (this specifically matters — `auth.js`'s session cookie only gets marked `secure` when this is set, which is required for the cookie to work over HTTPS).

Atlas network access needs to allow `0.0.0.0/0` ("allow from anywhere") since Render's free tier has no static outbound IP to allowlist instead.

`POST /api/import-garmin` (the local-folder Garmin import) will just harmlessly 404 with "No GPX files found" in this environment — `Garmin/` isn't part of git history and won't exist on Render. Not a bug, just means that specific admin action is dev-machine-only; `POST /api/import-gpx` (manual file upload) still works anywhere since it doesn't depend on a pre-existing local folder.
